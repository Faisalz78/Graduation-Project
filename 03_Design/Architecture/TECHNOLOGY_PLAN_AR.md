# مراحل البناء والتقنيات المستخدمة

الخطة التقنية لمطور واحد يستخدم البرمجة بمساعدة الذكاء الاصطناعي ولديه وقت للتنفيذ المتدرج، وآخر تحديث لحالتها 14 سبتمبر 2026. هذه الوثيقة تكمل خطة التنفيذ الفردي. المراحل شروط إنجاز وليست أسابيع. وصل التنفيذ إلى `0.17.0` باستخدام Next.js وFastAPI وPostgreSQL؛ تطبيق Expo الأولي مجمد مؤقتًا، والأدوات غير المنفذة تبقى مرشحة حتى تجتاز تجربة محددة.

الحالة الحالية: [دليل التشغيل](../../RUN_LOCAL_AR.md) و[قائمة التنفيذ](../../09_Project_Management/Team_Tasks/IMPLEMENTATION_BOARD_AR.md). نُفذت تجربة OCR وربطها بالموقع على عينات مصطنعة، وبُنيت الضوابط واللوحة وأول تطبيق جوال؛ لا تعد نتائج العينات المصطنعة دليلًا على الدقة في الفواتير الواقعية.

## القرار المعماري

نستخدم TypeScript للواجهات وPython للخادم والتحليل، مع PostgreSQL للبيانات. نبني الويب أولًا، ونكمل دورة الفاتورة، ثم نربط تطبيق الجوال بالخادم نفسه. يبقى الجوال جزءًا من التسليم المطلوب.

FastAPI هو مصدر قواعد العمل والصلاحيات والموافقات والحسابات. Next.js يعرض واجهة الويب ويتصل به، وExpo يفعل ذلك للجوال. يُقسم الخادم إلى وحدات داخل تطبيق واحد. عامل معالجة المستندات يعمل في عملية منفصلة ويستخدم وحدات Python المشتركة؛ لا تحتاج كل وحدة ذكاء خدمة مستقلة.

تُختار إصدارات مستقرة متوافقة وتُثبت في ملفات الاعتماد بعد تجربة تشغيل صغيرة. توافق PaddleOCR وPython ومكتبات الاستدلال يُختبر في بيئة خاصة بالعامل، ويمكن فصل اعتماداته عن اعتماديات API عند الحاجة.

## المرحلة الأولى المواصفات وتجربة المخاطر

التقنيات: Markdown للتوثيق، Mermaid لمخططات الحالات والعلاقات، Git لحفظ النسخ، ومستودع GitHub خاص عند بدء مشاركة أو حفظ الكود عن بعد. الرسم الأولي للشاشات بسيط ويكفي لاتخاذ قرارات التدفق.

نكتب الأدوار الثلاثة والصلاحيات وحالات الفاتورة وقواعد التعديل بعد المراجعة، ونرسم الجداول الأساسية. نجمع 10–20 عينة متنوعة كبداية مقترحة، ونجرب قراءة عربية وإنجليزية باستخدام Python وPaddleOCR وPyMuPDF. هذه تجربة محدودة؛ دمج الاستخراج في المنتج يأتي في المرحلة الرابعة.

الناتج: مواصفات قصيرة وعينة موسومة ونتيجة تجربة تشمل الحقول والبنود والزمن واستهلاك الذاكرة. نماذج OCR والتشابه الدلالي مرشحة للاختبار؛ لا نفترض دقتها من اسمها أو دعمها للغة.

شرط الانتقال: يمكن شرح المسار كاملًا، وعُرفت صعوبة الاستخراج على الجهاز والعينات المتاحة.

## المرحلة الثانية قاعدة البيانات والخادم والهوية

| التقنية | استخدامها |
|---|---|
| FastAPI | واجهات API وتطبيق الصلاحيات وقواعد العمل. |
| Pydantic | التحقق من شكل الطلبات والنتائج وتعريف الحقول المطلوبة. |
| PostgreSQL | المستخدمون والمشاريع والموردون والفواتير وبنودها والموافقات وسجل الإجراءات. |
| SQLAlchemy | التعامل مع الجداول والعلاقات والمعاملات من Python. |

| pytest | اختبار قواعد الهوية والصلاحيات والوصول للبيانات منذ هذه المرحلة. |

جهزنا التشغيل المحلي باستخدام PostgreSQL 17.11 المحمول داخل المشروع لأن Docker لم يكن متاحًا في البيئة المرصودة، مع الإبقاء على PostgreSQL نوعًا لقاعدة البيانات. نقطة الصحة والهوية وإدارة حسابات الشركة ومشاريعها وعضوياتها منفذة، مع أرقام نسخ وسجل تدقيق وحواجز للمهام المفتوحة. يمكن إضافة Docker Compose في مرحلة تهيئة النشر. تعتمد الصلاحية على الدور ونطاق المشروع أو الشركة.

تصميم الهوية يشمل انتهاء الجلسات وتجديدها وإلغاءها عند الحاجة. استخدام JWT وحده لا يطبق الصلاحيات تلقائيًا. للويب نستخدم نقلًا آمنًا للجلسة عبر HttpOnly وSecure مع حماية CSRF مناسبة إذا استُخدمت ملفات الارتباط للمصادقة؛ للجوال تخزين مناسب للرموز عبر SecureStore في مرحلته.

شرط الانتقال: تسجيل الدخول يعمل، والوصول غير المسموح يُرفض من API، ويمكن إنشاء المشروع والمورد وحفظهما في قاعدة البيانات.

الشاشات الأولى: الدخول، قائمة الفواتير، رفع فاتورة، تفاصيل الفاتورة وتعديلها، قائمة مراجعة مدير المشروع، ومراجعة المالية. نبدأ بإدخال بيانات يدوي أو مؤقت معلن لإكمال المسار، ثم نستبدله بالاستخراج الحقيقي.

الملفات تحفظ في مساحة خاصة دائمة على الخادم مع مراجع داخل PostgreSQL. API يتحقق من الصلاحيات عند الرفع والتنزيل. نستخدم واجهة تخزين واحدة حتى يمكن نقل الملفات لاحقًا إلى تخزين كائني خاص إذا احتاج النشر ذلك.

شرط الانتقال: فاتورة تمر من الرفع إلى الموافقة النهائية، وسيناريوهات الرفض وطلب التوضيح وإعادة الإرسال تعمل مع حفظ التاريخ. يجرب المسار على جهاز آخر ضمن بيئة تجريبية مضبوطة.

## المرحلة الرابعة استخراج المستندات وقراءة المصادر

| التقنية | استخدامها وحدودها |
|---|---|
| PaddleOCR | التعرف على النص في الصور وصفحات PDF الممسوحة. اختيار نموذج العربية وتكوين الاستخراج يتبع التجربة المبكرة. |
| PyMuPDF | قراءة نص PDF ومواقع الحروف مباشرة، وفحص مساحة الصور، وتحويل الصفحات الممسوحة إلى صور لـPaddleOCR. |
| pypdf | استخراج المرفقات من PDF، ومنها XML المضمن إن وجد. |
| lxml | قراءة XML بأسماء المساحات الصحيحة وإعدادات تمنع الكيانات الخارجية والوصول الشبكي غير المطلوب. |
| OpenCV | معالجة الصور الأساسية واكتشاف QR وقراءته. فك بيانات QR إلى حقول خطوة إضافية تعتمد على التنسيق. |
| Pydantic | تحويل المصادر إلى عقد موحد للفواتير، والتحقق من الحقول والبنود. |
| Celery وRedis | طابور مهام وعامل منفصل للاستخراج مع حالات معالجة وإعادة محاولة مدروسة. |

المسار: البحث عن XML مباشر أو مرفق أولًا، ثم قراءة نص PDF المتاح، ثم OCR عند الحاجة. نقرأ QR ونجمع مصادر الحقول لمقارنتها. الاحتفاظ بالنص والإحداثيات والثقة حيث تتوفر يساعد على ربط التصحيح بالدليل.

OCR ينتج نصًا ومواقع ودرجات ثقة متاحة؛ تعيين المورد والإجماليات وصفوف البنود إلى عقد الفاتورة يحتاج منطق استخراج إضافيًا واختبارًا على القوالب. إذا كانت دقة التخطيط ضعيفة، نجرب محلل مستندات جاهزًا مثل مكونات PaddleOCR المناسبة ضمن تجربة محددة بدل افتراض أن النص الخام سيكفي.

Celery يعمل داخل حاوية Linux على Windows، لأن المشروع لا يدعم التشغيل الأصلي على Windows. تُحفظ حالة المهمة ونسخة الفاتورة في قاعدة البيانات، مع مهلة وتعامل مع الفشل ومنع تكرار الأثر عند إعادة المحاولة. تُختبر إعادة التشغيل؛ الطابور وحده لا يضمن سلامة النتائج.

شرط الانتقال: رفع فاتورة فعلية ينتج حقولًا وبنودًا قابلة للمراجعة بجانب الأصل، وتظهر الأخطاء والفشل والثقة بوضوح، وتُحفظ التصحيحات دون فقد المصدر.

## المرحلة الخامسة التدقيق والضوابط المالية

التقنيات الأساسية: Python وDecimal للحسابات الدقيقة، PostgreSQL وNUMERIC للمبالغ، SQLAlchemy للمعاملات، hashlib لفحص تطابق الملف التام، وpytest لاختبار القواعد. هذه الوظائف وحدات داخل الخادم تستفيد من بيانات المرحلة الرابعة.

نبني بالترتيب: الحسابات والتقريب والضريبة القابلة للضبط، مقارنة حقول OCR وQR وXML، التكرار التام والمحتمل، ثم إثبات الاستلام الكامل والجزئي وأوامر الشراء وحدود الموافقة وفصل الصلاحيات والإشعارات الدائنة والمدينة ومراجعة بيانات الموردين.

حالة التنفيذ في `0.17.0`: اكتملت الحسابات والتكرار التام وهوية الفاتورة ومقارنة QR/XML والمطابقة الثلاثية وتحليل السعر والتكرار التقريبي، وحدود الموافقات والإشعارات والتحقق الداخلي من المورد، ثم كشف التجزئة ودرجة المخاطر واللوحة والميزانية وإدارة المشاريع والمستخدمين. بقيت حدود الموافقة حسب الفئة والمخاطر، والتصعيد والتحقق الرسمي.

التكرار المحتمل يجمع هوية المورد ورقم الفاتورة والتاريخ والمبلغ بعد التطبيع؛ بصمة الملف تكشف الملف المطابق فقط. تحفظ حالات الاشتباه بأسبابها للمراجعة. أي تحقق خارجي من المورد يعتمد على الوسيلة المصرح بها المتاحة.

نحمي انتقال الحالات من القرارات المتزامنة والنسخ القديمة. تعديل بيانات مؤثرة يعيد الفحوص والموافقات المطلوبة. يسجل حساب التطبيق الأحداث بطريقة إضافة فقط، وتوثق حدود صلاحيات الإدارة والنسخ الاحتياطي.

شرط الانتقال: حالات الحساب والتكرار والصلاحيات والاستلام والإشعارات المتفق عليها تنجح باختبارات محددة، ويمكن رؤية سبب كل نتيجة وتاريخ القرار.

نبني وظيفة واحدة في كل مرة: توحيد الاسم والوحدة والمواصفات؛ مقارنة السعر بتاريخ سابق مناسب؛ مقارنة الموردين مع مراعاة المنطقة والزمن؛ مقارنة البند بفئات المشروع وجدول الكميات وأوامر الشراء؛ كشف مجموعات تجزئة الفواتير؛ تجميع النتائج في مخاطر مفسرة؛ ثم عرض اللوحات والتنبيهات والتقارير.

حالة التنفيذ في `0.17.0`: تستخدم قاعدة التجزئة نافذة سبعة أيام وحد مدير المشروع، وتجمع درجة المخاطر تحذيرات الفحوص بأوزان ثابتة، وتعرض لوحة FastAPI وNext.js الأرقام المالية. أضيفت ميزانية مستقلة لكل مشروع وعملة وبنود BOQ، مع المعتمد والملتزم وقيد المراجعة والمتبقي وفحصي التصنيف والسعة. أضيفت مقارنة المنطقة من تاريخ الشركة الداخلي بعينة معلنة، وما زالت الأوزان والمقارنة تحتاج تقييمًا مستقلًا، وأضيفت التنبيهات داخل النظام وثلاثة تقارير CSV قابلة للتصدير.

المسار الهجين نُفذ في `0.17.0` داخل القارئ الحالي، مع الحفاظ على QR/XML والنتائج القديمة. [مواصفاته](../../02_Requirements/Use_Cases/HYBRID_TEXT_EXTRACTION_AR.md).

نبدأ بخط أساس لقواعد الفئات والأسعار، ثم نقيس هل التشابه الدلالي حسّن النتيجة. التشابه ليس حكمًا كافيًا على صلاحية المصروف. عند غياب المقارنات نعرض عدم كفاية البيانات. عتبات التنبيه تضبط على بيانات التطوير، ونتيجة المخاطر أولوية مراجعة وليست احتمال احتيال مثبتًا.

شرط الانتقال: النتائج مفهومة ومقيسة على مجموعة اختبار مستقلة، وأرقام اللوحات تطابق البيانات مع تعريف المدفوع والملتزم والمعلق والمتبقي ومنع العد المزدوج.

شرط الانتقال: موظف يكمل السيناريو على جهاز فعلي، ويرى مدير المشروع والمالية الأثر نفسه على الويب. نختبر صلاحيات الصور والملفات وانقطاع الشبكة وإعادة الإرسال. يمكن تقديم هذه المرحلة إذا احتاج العرض الأكاديمي تطبيق الجوال قبل اكتمال التحليلات.

النشر الأولي والتوثيق والاختبارات تدخل أثناء التطوير. هذه المرحلة تستكمل تقوية التشغيل وتقييم الاستخراج والمخاطر وقياس سهولة الاستخدام، وتعالج الأعطال وتجهز دليل المستخدم والتقرير والعرض. يحدد مزود الخادم وحجمه وتكلفته بعد قياس الذاكرة وزمن معالجة المستندات؛ لا تفترض هذه الخطة شراء خدمة أو نشر ملفات خارجية الآن.

شرط الاكتمال: تشغيل النسخة من التوثيق، نجاح سيناريوهات القبول والاسترجاع، وعرض النتائج الفعلية مع حجم البيانات وحدود التقييم.

## قواعد اختيار الأدوات والعمل مع المساعد

تدخل كل مكتبة عند الحاجة إلى مرحلتها. نعتمد التقنية عندما تجتاز تجربة صغيرة، ونوثق سبب أي تغيير. تبقى المعمارية وعقود البيانات ثابتة قدر الإمكان، وكل جلسة برمجة تستهدف ميزة محددة مع فحص مناسب ومراجعة للتغييرات وتجربة من الواجهة وحفظ في Git.

نماذج القراءة والتشابه مرشحة للاختبار وليست ضمانًا للدقة. خدمات النماذج الخارجية يمكن تقييمها لاحقًا إذا وجدت حاجة محددة وميزانية وموافقة على معالجة البيانات، ولا تعتمد عليها النسخة الأساسية في هذه الخطة. لا يتخذ مكون الذكاء الاصطناعي قرار الموافقة المالية.
